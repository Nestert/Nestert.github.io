# Добавление работ: инструкция агентам

Применяй эту инструкцию при добавлении работ, галерей, обложек и замене фотографий. Схему полей сверяй с `.pages.yml`, поведение страниц — с `.eleventy.js` и существующими карточками. Не меняй шаблоны и стили ради обычного наполнения.

## 1. Разобрать материалы

1. Прочитай `AGENTS.md`, проверь `git status --short`. Сохрани чужие изменения.
2. Составь соответствие: работа, категория, основное фото, дополнительные ракурсы, подпись.
3. Используй название, год, размеры, материалы, описание и серию из данных пользователя. Не угадывай их по фотографии или имени файла. Если не хватает обязательного названия, года или соответствия снимков работам, уточни это; пока готовь однозначно определённые материалы.
4. Несколько ракурсов одной работы оформляй одной карточкой с `gallery`. Отдельные произведения оформляй отдельными карточками.
5. Проверь, нет ли уже такой работы или фотографии. Не создавай дубликаты и не переименовывай существующие файлы без необходимости: имя Markdown определяет адрес страницы.

| Категория | Карточки | Фотографии |
| --- | --- | --- |
| Живопись | `src/content/paintings/` | `src/assets/images/paintings/` |
| Графика | `src/content/drawings/` | `src/assets/images/drawings/` |
| Объекты | `src/content/objects/` | `src/assets/images/objects/` |
| Ручные проекты | `src/content/projects/` | `src/assets/images/projects/` |

## 2. Подготовить и сжать фотографии

Сжимай **новые веб-копии до внесения в Git**, даже если сборка умеет оптимизировать изображения. Большие оригиналы иначе останутся в репозитории и его истории.

- Храни оригиналы пользователя отдельно от `src/`, `_site/` и `dist/`. Не удаляй и не перезаписывай их. Не складывай архивы, RAW, TIFF, HEIC и резервные копии в публикуемые каталоги.
- Запиши исходные размеры в пикселях, формат и вес каждого снимка. Учитывай поворот EXIF.
- Веб-копия: длинная сторона **не больше 2000 px**, пропорции сохранены, маленькие снимки не увеличены.
- Исправь ориентацию по EXIF. Не обрезай произведение, не растягивай, не применяй ретушь, фильтры или повышение резкости без запроса пользователя.
- Для обычных фотографий выбирай **JPEG, качество 82, progressive, mozjpeg**, либо **WebP, качество 82**. Расширение должно соответствовать реальному формату.
- При прозрачности используй WebP с альфа-каналом либо PNG. PNG оставляй, когда нужна прозрачность или сохранение тонких линий без потерь; непрозрачная фотография не требует PNG.
- Сохраняй корректный цветовой профиль. Пример ниже использует `keepIccProfile()`, как текущий скрипт сборки. Сравни цвет с оригиналом; не удаляй ICC вслепую. Не переноси EXIF/GPS через `keepMetadata()`.
- Рабочий ориентир веса фотографии — **200–800 КБ**. Файл больше **1 МБ** проверь отдельно: попробуй WebP или меньшую степень качества, сравни детали. Это ориентир, а не повод ухудшить произведение ради числа; обоснованное превышение укажи в отчёте.
- Уже подготовленную веб-копию, соответствующую требованиям, не перекодируй повторно без причины. При подборе качества каждый вариант создавай из оригинала.
- Для новых файлов используй понятные уникальные имена: `2026-work-name-01.jpg`, `2026-work-name-02.jpg`. Предпочитай строчные латинские буквы, цифры и дефисы. Не переименовывай старые файлы массово.

### Пример подготовки одного файла

Запускай из корня репозитория после установки зависимостей (`npm ci`, если `node_modules` отсутствует). Подставь реальный путь к оригиналу и **новое** имя веб-копии. Повтори для каждого выбранного снимка; существующий файл команда не заменит.

```bash
ORIGINAL='/absolute/path/to/original.jpg'
WEB_COPY='src/assets/images/paintings/2026-work-name-01.jpg'
node --input-type=module - "$ORIGINAL" "$WEB_COPY" <<'NODE'
import sharp from 'sharp';
import path from 'node:path';
import { mkdir, stat, writeFile } from 'node:fs/promises';

const [input, output] = process.argv.slice(2);
if (!input || !output || path.resolve(input) === path.resolve(output)) {
  throw new Error('Нужны разные пути оригинала и новой веб-копии.');
}
const extension = path.extname(output).toLowerCase();
if (!['.jpg', '.jpeg', '.webp', '.png'].includes(extension)) {
  throw new Error('Допустимы .jpg, .jpeg, .webp, .png.');
}
const before = await sharp(input).metadata();
if (before.hasAlpha && ['.jpg', '.jpeg'].includes(extension)) {
  throw new Error('Для прозрачного изображения выбери WebP или PNG.');
}
let pipeline = sharp(input)
  .rotate()
  .resize({ width: 2000, height: 2000, fit: 'inside', withoutEnlargement: true })
  .keepIccProfile();
if (extension === '.webp') {
  pipeline = pipeline.webp({ quality: 82, effort: 5 });
} else if (extension === '.png') {
  pipeline = pipeline.png({ compressionLevel: 9, adaptiveFiltering: true });
} else {
  pipeline = pipeline.jpeg({ quality: 82, progressive: true, mozjpeg: true });
}
const buffer = await pipeline.toBuffer();
await mkdir(path.dirname(output), { recursive: true });
await writeFile(output, buffer, { flag: 'wx' });
const after = await sharp(buffer).metadata();
console.log({
  input, output,
  before: { width: before.width, height: before.height, bytes: (await stat(input)).size },
  after: { width: after.width, height: after.height, bytes: buffer.length }
});
NODE
```

Проверь оригинал и веб-копию визуально: ориентацию, цвет, края, фактуру, тонкие линии и отсутствие заметных артефактов. Если декодер не читает исходный формат, сохрани оригинал и используй доступный локальный конвертер. Переименование расширения не конвертирует файл.

### Что делает существующая сборка

`npm run build` запускает Eleventy, затем `scripts/optimize-published-images.mjs`, затем подготовку `dist/`.

- Eleventy создаёт адаптивные варианты в `_site/assets/images/optimized/`: для карточек ширины 320/640/960/1200, для страниц работ — 800/1200/1600.
- Скрипт дополнительно обрабатывает JPG/JPEG/PNG/WebP из `src/assets/images/` и пишет результат по тем же относительным путям в `_site/assets/images/`.
- Предел скрипта — 2000 × 2000 с сохранением пропорций и без увеличения. JPEG/WebP имеют качество 82, PNG — сжатие 9.
- Если исходник уже помещается в предел и перекодирование не уменьшает вес, остаётся скопированный исходный файл.
- `src/assets/images/` не изменяется. Полноэкранный просмотр использует публичный путь изображения, поэтому проверяй и эту копию.
- `npm run optimize:images` запускает только последний этап сжатия изображений; он не заменяет полную сборку. `npm run dev` также не запускает этот этап.

Не добавляй отдельный оптимизатор или новую зависимость для обычного наполнения. Не редактируй `_site/`, `dist/` и автоматически созданные варианты вручную.

## 3. Создать карточку

Имя нового файла: `src/content/<category>/<year>-<slug>.md`. Проверь уникальность. Макет и адрес наследуются из `<category>.11tydata.js`; не дублируй `layout` и `permalink`.

Пример структуры, **не готовая работа**. Замени условные значения реальными; необязательные поля без данных удали.

```yaml
---
title: "Название работы"
year: 2026
dimensions: "50 × 70 см"
materials: "бумага, тушь"
series: "Существующее или согласованное название серии"
description: "Описание из материалов пользователя."
image: "/assets/images/drawings/2026-work-name-01.jpg"
gallery:
  - "/assets/images/drawings/2026-work-name-02.jpg"
thumbnail_position:
  x: 50
  y: 50
  zoom: 100
order: 0
---

Необязательный дополнительный текст в Markdown.
```

- Обязательны `title`, числовой `year`, существующее `image`. Остальные сведения добавляй при наличии.
- `image` — первый снимок; `gallery` — список путей к дополнительным снимкам, до 20, без дублей и без повторения `image`.
- В публичных путях не должно быть `src/`, абсолютного пути компьютера или `file://`.
- `thumbnail` добавляй только для отдельной обложки. Если он отсутствует, используется `image`; не создавай копию того же снимка ради миниатюры.
- `thumbnail_position`: X/Y от 0 до 100, масштаб от 100 до 300. Подбирай кадр в `/admin/thumbnail/`, не обрезая основное фото. По умолчанию — 50/50/100.
- Размеры произведения не равны размерам снимка в пикселях. Единицы измерения бери из подписи пользователя.
- Не дублируй один текст в `description` и теле Markdown. `description_en` заполняй только при наличии перевода или запроса на него.

## 4. Учесть серию, обложку и порядок

- `series` в живописи, графике и объектах автоматически создаёт серию на `/projects/series/<slug>/`. Для обычной серии не нужна дополнительная карточка в `projects`.
- Сверяй название серии с существующими: регистр и лишние пробелы при группировке игнорируются, но разные написания могут создать две серии.
- Ручной проект с `series`, совпадающей с автоматической серией, входит в неё: его основное фото и галерея добавляются к слайдам серии. На странице проектов он не дублируется отдельной карточкой.
- У обычных работ в слайды серии входит только `image`; их `gallery` остаётся на отдельных страницах.
- Ручные обложки находятся в `src/_data/series-covers.json`. Не заменяй существующую обложку без причины. Новая работа может изменить автоматическую обложку: проверь результат. Приоритет без ручной настройки: миниатюра/фото первого связанного ручного проекта, затем миниатюра/фото самой новой работы.
- Порядок задаётся в `src/_data/work-order.json`. В массивах `paintings`, `drawings`, `objects` находятся полные пути `src/content/.../*.md`.
- Общий список проектов — `project_items`: `{"type":"series","series":"Название"}` либо `{"type":"project","project":"src/content/projects/2026-name.md"}`. Не добавляй дубликаты и не создавай параллельный список `projects` вместо `project_items`.
- Если пользователь задал место новой работы, вставь путь в нужную позицию, сохранив взаимный порядок остальных. Без указания места оставь резервную сортировку: не перечисленные работы показываются после перечисленных, по `order`, затем году от нового к старому и названию.
- В категориях работы одной серии собираются в блок; место блока определяется первой работой этой серии в списке. Учитывай это при проверке порядка.

## 5. Проверить и передать результат

1. Проверь, что все новые `image`, `gallery`, `thumbnail` и обложки существуют в `src/`. Для переименованных файлов найди и обнови все ссылки, включая JSON и Markdown.
2. Выполни `npm run check`. Успешная сборка не заменяет визуальную проверку.
3. Через `npm run dev` проверь категорию, страницу каждой новой работы и серию, если она задана. Проверь мобильную и широкую ширину: подписи, миниатюры, порядок, карусель и увеличение фотографий.
4. Отдельно проверь в `_site/` размеры и вес опубликованных копий новых фотографий: dev-сервер не воспроизводит весь этап сжатия. Убедись, что файлы читаются и длинная сторона не превышает 2000 px.
5. Выполни `git diff --check` и просмотри `git diff --stat` / `git status --short`. В изменениях должны быть только нужные карточки, веб-копии и согласованные настройки порядка/обложек. Не включай оригиналы, архивы и результат сборки.
6. В отчёте укажи добавленные работы и локальные URL, число фотографий, размеры/вес до и после сжатия, результат сборки и визуальной проверки. Невыполненные проверки обозначь явно.
7. Публикуй только в рамках запроса пользователя. Push в `main` автоматически публикует сайт через GitHub Actions в Yandex Object Storage; `npm run deploy` в проекте отсутствует.
